### **Rebasing in Git**

Git **rebasing** is an alternative to merging that helps keep a clean, linear project history. Instead of creating a merge commit, rebase moves commits from one branch onto another, **rewriting history** in the process.

---

### **1. Basic Concept of Rebase**

Rebasing moves the commits of a feature branch **on top** of another branch (usually `main` or `develop`). It **reapplies** each commit one by one, creating new commit hashes.

📌 **Command:**

`git checkout feature-branch git rebase main`

🔹 Git removes commits from `feature-branch`, applies all `main` updates first, then **reapplies** the feature commits.

✅ **Result:** Cleaner, linear history.  
❌ **Risk:** Can rewrite history, causing conflicts.

---

### **2. Interactive Rebase (`git rebase -i`)**

Interactive rebase lets you **modify commit history** before applying changes.

📌 **Command:**

`git rebase -i HEAD~5  # Modify last 5 commits`

🔹 Options inside the rebase editor:

- `pick` → Keep commit
- `reword` → Edit commit message
- `edit` → Modify the commit
- `squash` → Merge with the previous commit
- `drop` → Remove commit

✅ **Use Case:** Cleaning up commits before merging (e.g., squashing multiple small commits).

---

### **3. Rebase vs. Merge**

| Feature       | Rebase                               | Merge                           |
| ------------- | ------------------------------------ | ------------------------------- |
| History       | Linear, cleaner history              | Branching with merge commits    |
| Commit hashes | Rewrites commit history              | Preserves original commits      |
| Conflict risk | Higher, especially in long branches  | Lower, but history gets messy   |
| Use case      | Keeping history clean before merging | Keeping a full record of merges |

📌 **Rule of Thumb:**  
🔹 Use **merge** for preserving branch history.  
🔹 Use **rebase** for keeping history clean before merging.

---

### **4. Handling Rebase Conflicts**

If conflicts arise during rebasing:

`git status  # See conflicting files git add <fixed-files>  # Mark conflicts as resolved git rebase --continue  # Continue the rebase`

Or, if needed:

`git rebase --abort  # Cancel rebase and go back to original state`

---

### **5. Golden Rule of Rebasing**

❌ **Never rebase a shared branch (like `main`) if others are working on it!**  
Rewriting history will **break other people's work**.

✅ **Use rebase safely:**

- Locally, before merging a feature branch.
- When syncing your branch with `main` (`git pull --rebase`).
- For cleaning up commit history before submitting a PR.

---

### **🔍 Summary:**

✅ **Use rebase for:** Clean, linear history.  
✅ **Use interactive rebase for:** Editing commits before merging.  
✅ **Avoid rebasing shared branches** to prevent conflicts
