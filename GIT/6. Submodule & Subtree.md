### **Submodules and Subtrees in Git**

When working with Git, sometimes you need to include **external repositories** inside your project. Two main approaches exist: **Git Submodules** and **Git Subtrees**. Both allow you to manage dependencies but function differently.

---

## **1. Git Submodules**

A **Git Submodule** is a way to include another repository inside your main repository while keeping its history separate. It links to a specific commit of the external repository, making updates **manual**.

### **1.1 When to Use Submodules**

✅ When you need a **strictly versioned dependency** (e.g., a library or SDK).  
✅ When you don’t want to mix external code with your main repository’s history.  
✅ When multiple projects rely on the same external repository but need different versions.

### **1.2 Adding a Submodule**

To add a submodule inside your project:

`git submodule add https://github.com/example/repo.git path/to/submodule`

🔹 This creates a `.gitmodules` file that tracks submodules.  
🔹 The **submodule directory** is linked to a specific commit, not a branch.

### **1.3 Cloning a Repository with Submodules**

By default, `git clone` doesn’t pull submodules. To include them:

`git clone --recurse-submodules https://github.com/example/main-repo.git`

Or, if you already cloned the repository:

`git submodule update --init --recursive`

### **1.4 Updating a Submodule**

If the submodule repository has new changes:

`cd path/to/submodule git pull origin main  # Update to latest commit in the submodule cd ../ git add path/to/submodule git commit -m "Updated submodule to latest commit"`

🔹 You need to manually commit the submodule update in the main repository.

### **1.5 Removing a Submodule**

`git submodule deinit -f path/to/submodule rm -rf path/to/submodule .git/modules/path/to/submodule git rm -f path/to/submodule git commit -m "Removed submodule"`

---

## **2. Git Subtrees**

A **Git Subtree** is a way to embed another repository inside your project **while keeping it as part of your main repository’s history**. Unlike submodules, subtrees allow you to merge and push changes more naturally.

### **2.1 When to Use Subtrees**

✅ When you want to **avoid dealing with separate Git history** for dependencies.  
✅ When you want **easier merging and pushing** between your project and the external repository.  
✅ When contributors **don’t need extra Git knowledge** to work with dependencies.

### **2.2 Adding a Subtree**

To add an external repository as a subtree:

`git subtree add --prefix=path/to/subtree https://github.com/example/repo.git main --squash`

🔹 The `--prefix` specifies where to place the subtree.  
🔹 The `--squash` option combines commits into a single commit to keep the history clean.

### **2.3 Updating a Subtree**

If the external repository has new changes:

`git subtree pull --prefix=path/to/subtree https://github.com/example/repo.git main --squash`

🔹 This merges the latest changes from the subtree repository into your project.

### **2.4 Pushing Changes Back to Subtree Repository**

If you made changes in the subtree and want to push them back:

`git subtree push --prefix=path/to/subtree https://github.com/example/repo.git main`

🔹 This sends your changes **back to the original repository**.

### **2.5 Removing a Subtree**

Just delete the folder and commit the change:

`rm -rf path/to/subtree git commit -m "Removed subtree"`

---

## **3. Submodules vs. Subtrees: Key Differences**

|Feature|Submodules|Subtrees|
|---|---|---|
|**Dependency Versioning**|Tracks a **specific commit** of the external repo|Integrates the external repo into the main repo|
|**Ease of Use**|Harder to work with (requires `git submodule`commands)|Works like a normal folder inside the repo|
|**History**|Maintains separate history|Merges history into the main repository|
|**Updating**|Requires manually updating submodule commits|Can be updated with `git subtree pull`|
|**Cloning**|Needs `git submodule update --init` after cloning|Clones like a normal repository|
|**Use Case**|Best for shared libraries or dependencies|Best for deeply integrated codebases|

---

## **4. Which One Should You Use?**

🔹 **Use Submodules** if:

- You want to **keep the external repository separate** from your main repo’s history.
- You need **strict version control** over the dependency.
- The external repository is **actively developed and used in multiple projects**.

🔹 **Use Subtrees** if:

- You want **a simpler workflow** without extra Git commands.
- The external repo is **tightly integrated** into your project.
- You frequently modify the external code **inside your main repository**.

---

### **Conclusion**

✅ **Submodules** keep dependencies separate but require extra management.  
✅ **Subtrees** merge dependencies into the main repository, making updates easier.  
✅ If you **just need a dependency**, **Submodules** are better.  
✅ If you **actively work on the dependency**, **Subtrees** are more practical.
